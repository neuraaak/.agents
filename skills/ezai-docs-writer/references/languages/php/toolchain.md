# PHP Docs Toolchain — Recommended Stack & Canonical Configs

Load this file when **choosing the documentation tooling** for a PHP project, or when **scaffolding the docs config from scratch**. It defines the recommended tool stack and copy-paste canonical configs.

For the operational rules behind these choices — running the generators, multi-version, CI deploy, anti-patterns — load `plugins-deploy.md`. This file is the *what to install and what the config looks like*; `plugins-deploy.md` is the *how to run and deploy it*.

---

## Recommended stack

PHP doc generators render the **API reference only** (HTML from PHPDoc). There is no PHP-native equivalent of MkDocs/VitePress for prose, so the canonical stack is **two tools**: an API generator plus a prose site generator.

| Tool            | Role                                | Why it is the default                                             |
| :-------------- | :---------------------------------- | :---------------------------------------------------------------- |
| `phpDocumentor` | API reference from PHPDoc (mature)  | De-facto standard for 20 years; static reflection, no code exec   |
| `Doctum`        | API reference from PHPDoc (new-gen) | Maintained Sami fork; incremental cache, PHP config, Git versions |
| `VitePress`     | Prose site (guides, tutorials)      | Same prose stack as the JS skill — Markdown-native, fast, search  |

Pick the **API generator** by project posture:

- **phpDocumentor** — existing projects, PHPDoc/PSR-5 conformance, when HTML/XML/RST/Markdown output or Composer/PHAR/Docker integration matters. Output theme is dated but the parser is the reference.
- **Doctum** — new projects that want fast incremental builds (diff cache), a PHP (not XML) config, and **built-in Git branch/tag multi-versioning** without an external tool. API-only, Symfony-community adoption.

Add **VitePress** for prose only when the project needs guides/tutorials beyond the API dump — the API generator handles the reference, VitePress owns the narrative pages. The Diátaxis templates in `common/quadrants-templates.md` assume a Markdown prose tool (VitePress or MkDocs Material).

Reach for **MkDocs Material** instead of VitePress for prose if the team already standardized on it elsewhere — both are interchangeable at the prose layer.

## Canonical phpDocumentor config (`phpdoc.dist.xml`)

Copy as the baseline. Replace every `<project>` / `<owner>` token — derive each value from the project. Commit as `phpdoc.dist.xml`; a local `phpdoc.xml` overrides it and stays git-ignored.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<phpdocumentor
    configVersion="3"
    xmlns="https://www.phpdoc.org/xsd/phpdocumentor/3.0/phpdocumentor.xsd">
  <title><Project> API</title>
  <paths>
    <output>docs/api</output>
    <cache>.phpdoc/cache</cache>
  </paths>
  <version number="1.0.0">
    <api>
      <source dsn=".">
        <path>src</path>
      </source>
      <output>.</output>
      <visibility>public</visibility>
      <visibility>protected</visibility>
    </api>
  </version>
</phpdocumentor>
```

## Canonical Doctum config (`doctum.php`)

```php
<?php

use Doctum\Doctum;
use Symfony\Component\Finder\Finder;

$iterator = Finder::create()
    ->files()
    ->name('*.php')
    ->exclude(['tests', 'vendor'])
    ->in(__DIR__ . '/src');

return new Doctum($iterator, [
    'title'      => '<Project> API',
    'build_dir'  => __DIR__ . '/docs/api',
    'cache_dir'  => __DIR__ . '/.doctum-cache',
    'source_dir' => __DIR__,
    // Git multi-versioning: point at branches/tags instead of a flat source.
    // 'versions' => GitVersionCollection::create(__DIR__)->addFromTags('v*'),
]);
```

For the VitePress prose config (`docs/.vitepress/config.mts`), reuse the canonical config in `languages/javascript/toolchain.md` verbatim — only the API pages differ (generated by phpDocumentor/Doctum into `docs/api/` instead of TypeDoc).

## Best practices encoded in these configs

These are the load-bearing decisions — keep them when adapting the config.

- **Commit the `.dist` config, git-ignore the local override.** `phpdoc.dist.xml` / `doctum.php` are versioned; a developer's `phpdoc.xml` overrides locally without touching CI.
- **Always set a cache dir.** Both generators are slow on large codebases without `cache` / `cache_dir` — incremental builds depend on it. Doctum's diff cache is its main speed advantage; don't disable it.
- **Static reflection only — never execute the code.** Both parse PHPDoc via reflection. Autoload errors in `src/` still break parsing, so the project must be `composer install`-clean before a docs build.
- **Scope visibility deliberately.** phpDocumentor's `<visibility>` and Doctum's `@internal` filtering control what the reference exposes — emit the public/protected surface, hide internals (mirror the `@api`/`@internal` tags from `standards.md`).
- **Doctum owns its own versioning.** Use `GitVersionCollection` for multi-version instead of bolting on an external tool — see `plugins-deploy.md`. phpDocumentor versions via the `<version>` element per release build.
- **Output into the docs tree.** Generate API HTML into `docs/api/` so a prose tool (VitePress) can host both narrative and reference under one site.
